# 《基于Web的一体化协同白板、语音聊天与文件传输系统》开题报告大纲

## 一、 提出问题（研究背景与意义）

- **1.1 研究背景**

  - 线上小组学习、远程项目讨论已成为常态。

  - 当前协作工具呈现“碎片化”特征：白板用Miro，语音用腾讯会议/Discord，文件传微盘/微信。

- **1.2 核心问题**

  - **上下文断裂**：在不同工具间频繁切换，导致讨论思路被打断，效率低下。

  - **信息孤岛**：语音里说的内容无法直接在白板上呈现，白板上产生的文件无法直接分发给正在语音的组员。

  - **部署与使用门槛**：复杂的网络配置（如局域网共享、内网穿透）超出了普通学生的技术能力。

- **1.3 研究目标**

  - 构建一个**零配置、开箱即用**的Web协作平台。

  - 实现“白板+语音+文件”三大功能的深度集成，提供沉浸式的协作体验。

## 二、 解决痛点（需求分析与场景定位）

- **2.1 目标场景**

  - 跨地域的小组学习、线上科研讨论、远程代码/架构评审。

- **2.2 现有痛点与解决思路**

  - **痛点1：工具割裂** -> **对策**：单页面集成。白板、语音、文件面板在同一界面，语音状态与白板光标实时联动。

  - **痛点2：公网传输慢/不稳定** -> **对策**：采用WebRTC技术进行公网P2P传输（辅以TURN中继），或采用高效的分片HTTP上传，优化公网带宽利用率。

  - **痛点3：协同冲突** -> **对策**：设计基于WebSocket的高效同步协议，解决多人同时画图、发消息的状态一致性问题。

## 三、 技术实现（核心内容细化——纯公网一体化架构）

*(此部分重点展示如何利用公网协议实现功能结合)*

- **3.1 系统整体架构（纯公网B/S架构）**

  - **客户端**：浏览器（HTML5 Canvas, WebRTC API, Fetch API）。

  - **公网服务端**：

    - **信令与状态服务器**：Node.js + WebSocket（负责房间管理、白板同步、聊天、WebRTC信令交换）。

    - **媒体中继服务器**：Coturn（STUN/TURN），解决公网复杂网络环境下的NAT穿透与媒体中转。

    - **文件存储服务器**：基于HTTP的静态资源服务，支持大文件分片上传。

- **3.2 模块一：协同白板与文字聊天（基于WebSocket）**

  - **通信协议设计**：自定义JSON/Protobuf消息格式。区分`Draw`、`Erase`、`CursorMove`、`Chat`等事件类型。

  - **并发同步控制**：引入 **CRDT（无冲突复制数据类型）** 算法，确保多人同时绘制时，公网延迟下白板状态最终一致，避免“你画一笔我擦一笔”的覆盖冲突。

  - **光标与聊天集成**：光标位置高频同步（需节流优化），聊天消息实时广播，支持在聊天框中发送白板快照。

- **3.3 模块二：语音聊天室（基于WebRTC + 公网TURN）**

  - **信令控制**：通过公网WebSocket完成SDP交换与ICE候选者交换。

  - **拓扑与公网适应**：采用 **Mesh（网状）架构**（适合<10人小组）。由于全公网环境复杂，必须部署STUN/TURN服务器。优先尝试P2P直连，失败时自动降级为TURN服务器中继转发，保证100%连通率。

  - **音频优化**：开启WebRTC自带的回声消除（AEC）、噪声抑制（NS），并针对公网抖动引入Jitter Buffer（抖动缓冲）优化。

- **3.4 模块三：文件传输（HTTP分片 + WebRTC DataChannel）**

  - **公网HTTP分片上传**：将文件切割为固定大小的Chunk（如2MB），通过HTTP POST并发上传至公网服务器，支持断点续传。

  - **实时P2P分发**：对于正在语音的组员，可利用WebRTC DataChannel进行文件P2P直传（或经TURN中转），减少服务器带宽压力。

- **3.5 核心亮点：功能的深度结合（Integration）**

  - **白板拖拽上传**：用户可将文件直接拖拽到白板区域，图片自动生成预览并钉在白板上，其他文件生成可点击的图标。

  - **语音状态同步**：谁在说话，其对应的白板光标旁会显示声波闪烁动画，增强临场感。

  - **聊天与文件联动**：在聊天室发送文件，文件自动同步到白板的文件面板中。

  - **一键快照**：语音讨论结束时，一键将白板内容与聊天记录打包生成PDF/图片，分发给组员。

- **3.6 关键技术难点与对策**

  - **难点**：公网环境下WebRTC的NAT穿透成功率低。

  - **对策**：搭建Coturn服务器，配置STUN用于发现公网地址，TURN用于对称型NAT的流量中转，确保语音和P2P文件传输的连通性。

  - **难点**：高频白板操作导致公网WebSocket带宽激增。

  - **对策**：前端采用节流（Throttling）与防抖，后端采用增量广播（只发变化部分），并引入二进制协议（如MessagePack）压缩数据体积。

## 四、 实验设计与性能评估

*(去除局域网对比，聚焦公网环境下的表现)*

- **4.1 实验环境**

  - 公网服务器（如阿里云/腾讯云轻量应用服务器，2核4G，带宽5Mbps）。

  - 测试客户端：不同网络环境（校园网、家庭Wi-Fi、4G/5G热点）。

- **4.2 核心实验指标**

  - **操作同步延迟**：测量公网环境下，A端绘图到B端渲染的时间差（目标：<200ms）。

  - **并发人数与稳定性**：测试5人、10人、20人同时在线时，WebSocket消息丢失率、服务器CPU/内存占用、语音卡顿率（MOS评分）。

  - **文件传输速度**：测试公网HTTP分片上传在5Mbps服务器带宽下的实际传输速率（受限于服务器带宽），以及WebRTC DataChannel P2P直传的成功率与速度。

- **4.3 预期结果**

  - 实现MVP（多人绘图、光标同步、语音、资料上传）功能全覆盖。

  - 系统在纯公网环境下具备高可用性，NAT穿透成功率达到80%以上，TURN中继降级平滑无感知。

## 五、 研究计划（进度安排）

- **第一阶段（第1-2周）**：需求分析与原型设计，确定纯公网Web架构，完成UI原型。

- **第二阶段（第3-5周）**：搭建Node.js公网信令服务器，完成WebSocket白板同步、光标同步与文字聊天。

- **第三阶段（第6-8周）**：部署Coturn服务器，集成WebRTC语音通话与P2P文件传输，实现公网NAT穿透。

- **第四阶段（第9-10周）**：功能整合（白板拖拽上传、语音状态联动），系统联调与公网性能测试。
