# 《基于Web的协同白板与实时音视频及局域网快传系统》开题报告大纲

## 一、 提出问题（研究背景与意义）

- **1.1 研究背景**

  - 线上/混合式学习与宿舍、教室中的小组讨论已常态化，协作的核心动作是“边讲边画、随手把资料递给对方”，理想状态下这三件事应在同一个页面内连贯完成。
  - 现有工具碎片化：白板（Miro 等）、语音（腾讯会议/Discord 等）、文件传输（微信/网盘等）彼此独立，切换频繁；文件走公网中转时速度受服务端出口带宽与计费策略限制，大文件体验尤其差。
  - 浏览器能力已足以支撑本课题：WebRTC（媒体流与 DataChannel）、Canvas/WebGL、File System Access API 均为稳定标准，“零安装”的实时协作在工程上已可行。

- **1.2 核心问题（研究问题）**

  - **Q1 一致性**：多人并发绘图时如何保证状态收敛（不覆盖、不漂移、不丢笔画），同时把实现与调试成本控制在可行范围内？
  - **Q2 局域网直传的可行性边界**：在“纯浏览器 + 有限 JavaScript 权限”的约束下，数据通路能从公网中转推进到同网段直传到什么程度？其吞吐上限由哪些因素决定？
  - **Q3 多负载共存时的资源分配**：白板、实时语音、文件传输共用同一页面与浏览器进程时，如何按优先级分配带宽与算力（语音 > 交互延迟 > 文件吞吐）？

- **1.3 研究目标与验收指标**

  - 目标：构建无需安装客户端、浏览器即可使用的协同空间，支持多人绘图、实时语音与文件共享，并给出可复现的性能数据。
  - 同步延迟：局域网 5 人房间内，绘图操作端到端延迟 p50 < 100 ms、p95 < 200 ms。
  - 文件传输：局域网直传路径下 100 MB 文件平均速率达到物理链路带宽的 60% 以上（千兆以太网下不低于 75 MB/s）；若走 WebRTC DataChannel 而受其流控限制，则如实报告实测上限并给出瓶颈归因，作为工程取舍依据。

- 交付物：系统本体 + 可复现的测试方案 + 原始数据与分析结论。

## 二、 解决痛点（需求分析与场景定位）

- **2.1 目标场景**

  - **小组学习/项目讨论（3–6 人）**：需要实时画图推导、同步讲解、随手分享资料。
  - **宿舍/教室内网协作（同一网段）**：外网质量差或计费敏感时，依赖局域网完成大文件分发。

- **2.2 现有痛点**

  - **操作割裂**：语音时看不到对方在画什么，画图时又要切窗口或挂断，讲解与操作不同步。
  - **文件传输慢且受制于第三方**：公网网盘中转慢、有大小与速度限制；宿舍内两台相邻设备之间传 1 GB 文件也要绕公网一圈。
  - **并发与同步冲突**：多人同时绘图时出现光标漂移、笔画覆盖、状态不一致。
  - **隐私与外部依赖**：资料必须上传到第三方服务器；无外网时整个协作链路直接失效。

- **2.3 本课题的解决方案（思路）**

  - **三位一体**：白板（视觉）+ 语音（听觉）+ 文件（资料）在同一页面内集成，以“房间”为协作单元。
  - **一致性方案**：以 CRDT（无冲突复制数据类型）为主线、OT 作为对照讨论，配“快照 + 增量”同步，降低并发收敛的实现与验证成本。
  - **传输分两级**：默认走自托管节点（可在局域网内任一台设备上以 Docker 一键启动）的 HTTP 直传，速率接近链路上限；同时提供 WebRTC DataChannel 的纯 P2P 通道，并在界面上明确显示“直连 / 中转”状态。
  - **降级优先**：直连不可用时自动回落到服务器中转，保证“可用优先、性能其次”。

## 三、 技术实现（核心内容细化）

- **3.1 系统整体架构设计**

  - **前端**：HTML5 Canvas（图形以矢量对象存储、分层渲染与命中检测，而非像素级绘制）、WebRTC API（音频/可选视频、DataChannel）、Fetch + File API（文件分片）。
  - **后端**：Node.js（Express + Socket.IO）承担信令、房间管理与 HTTP 文件服务。选型理由：单一语言栈可缩短 MVP 周期；Go 的高并发优势在本课题（房间数、人数均很小）不构成瓶颈，故本期不引入，若后续信令并发成为瓶颈再评估重写热点模块。
  - **通信层**：WebSocket（信令与状态同步）、WebRTC（媒体流与 P2P 数据）、HTTP（文件上传/下载）。
  - **存储层**：SQLite 保存用户、房间、消息与文件元数据；大文件默认不落盘（直传），仅小文件与需要离线访问的资料保留在节点上，并设置容量上限与过期清理。
  - **部署形态（关键约束）**：系统由“一个可自托管的轻量节点 + 若干纯浏览器客户端”组成。节点可运行在房间内任意一台电脑或树莓派上（Docker 一键启动），其他成员无需安装任何客户端；这意味着系统不依赖公网服务器，但需要明确“节点所在设备”的可用性前提。
  - **安全上下文约束**：getUserMedia、WebRTC、剪贴板与文件系统相关 API 只在安全上下文（HTTPS 或 localhost）下可用，因此自托管节点必须提供 HTTPS（内网自签证书需一次性信任，或使用带公网域名的正式证书）。该约束是部署文档必须交代的前置条件，也是“局域网直传”方案能否落地的关键前提。

- **3.2 模块一：协同白板与光标同步（基于 WebSocket）**

  - **通信协议设计**：自定义 WebSocket 消息格式（JSON 控制消息 + 二进制高频消息），区分事件类型（Draw/Erase/Move/Cursor/Undo/Snapshot），消息头携带房间号、客户端标识、序号与时间戳，便于调试、去重与重放。
  - **并发一致性**：采用 CRDT 路线——以“图形（stroke/shape）”为最小并发单元，配 last-write-wins 的增删语义。选型理由：白板操作以“增删/移动一个图形”为主，不需要文本文档式的位置变换；OT 需要中心化变换服务与严格因果序，实现与验证成本显著更高，对本项目的收益有限（OT 作为对照方案在报告中讨论，不作为主线）。
  - **同步策略**：新成员加入时下发状态快照（序列化后的图形数组，而非历史操作序列，避免回放的复杂度与版本耦合）；此后只广播增量事件。Undo 采用各端本地栈 + 反向事件，不做全局撤销（全局撤销需与并发语义配套，超出本期范围）。
  - **光标同步**：发送前将坐标归一化到画布逻辑坐标（0–1）并量化，发送频率限制在 30–60 Hz（低于该频率视觉上已连续），接收端做插值与平滑，避免“瞬移”。
  - **文字聊天室（附加功能，非研究重点）**：复用同一 WebSocket 通道，消息由服务端持久化到 SQLite 并支持历史拉取；实现成本低，但只作为完整性功能，不占用实验篇幅。

- **3.3 模块二：实时语音（视频为可选开关，基于 WebRTC）**

  - **信令控制**：通过 WebSocket 完成房间成员协商、SDP 交换与 ICE 候选交换。
  - **拓扑选型**：面向 3–6 人的小组场景采用 Mesh 网状架构（P2P 直连），服务器只做信令，降低服务器负载与媒体转发延迟。
  - **Mesh 的边界（本期上限）**：Mesh 下每个客户端需向其余每个成员各发一路音频并独立编码，随人数增长，先到瓶颈的是上行带宽与移动端 CPU（而非服务器）。因此本期将 Mesh 人数上限定为 6 人左右；超出上限的扩容方案（SFU，如 LiveKit/mediasoup/Janus）列入风险预案与后续工作，不在本期实现，也不宣称“20 人可用”。
  - **音频处理**：开启 WebRTC 自带的回声消除（AEC）、噪声抑制（NS）与自动增益控制（AGC）；移动端注意自动播放策略需由用户手势触发。
  - **视频说明（与课题名称的对齐）**：课题方向为“实时音视频”，但 MVP 先实现语音——在同一 PeerConnection 上增加视频轨道即可扩展，改造成本低；视频会显著占用带宽并加剧移动端 CPU 压力，故本期作为可选开关，并在实验中做“仅语音 / 语音+视频”的简单对比。
  - **质量目标**：单向端到端延迟 < 200 ms（ITU-T G.114 给出的交互可接受区间），抖动缓冲自适应。

- **3.4 模块三：文件传输（HTTP + 局域网快传）**

  - **基础文件上传**：HTTP 分片上传（固定 4–8 MB 分片、并发 2–4 路），前端显示进度与实时速率；服务端按分片序号落盘并记录分片位图，支持断点续传（浏览器刷新或中断后按位图继续）；下载端支持 Range 请求。
  - **局域网直传（核心亮点，分两条路径）**：
    - **路径 A：局域网 HTTP 直传（主力路径，速度最优）**。自托管节点在局域网内提供 HTTP/HTTPS 服务，客户端直接与该节点通信，数据不出内网，速率可接近物理链路上限（千兆下实测通常在 100 MB/s 量级）。
    - **路径 B：WebRTC DataChannel P2P 直传（纯浏览器，不经任何自托管服务）**。以 DataChannel 分片传输，用缓冲水位（bufferedAmount/bufferedAmountLowThreshold）做背压控制，收发两端各算一次 hash 校验。性能上限受浏览器 SCTP 实现与窗口设置影响，需实测界定。
    - **一个必须澄清的技术约束**：浏览器 JavaScript **无法发起 UDP 广播或 mDNS 查询**，所以“浏览器端自己做局域网发现”这一常见设计并不可行。本方案把发现动作下沉到原生服务：由自托管节点上的 mDNS/UDP 广播发布服务，浏览器侧通过一次信令或已知地址获得节点入口，再据此建立局域网直传通路。
    - **直连判定与呈现**：通过 ICE 的 selected candidate pair 判断实际通路（两侧均为 host 且处于同一私网段即视为局域网直连），界面显示“直连/中转”标识，既便于实验统计，也让用户理解当前性能来源。
  - **安全与限流**：房间采用短期 token 鉴权（同一网段的其他设备也能发现节点，必须有准入控制）；DataChannel 本身由 DTLS 加密；自签证书场景需给出用户提示；单文件大小上限、最大并发数、过期清理策略在配置中显式声明。

- **3.5 关键技术难点与解决方案**

  - **难点1：多人房间的消息广播放大与前端渲染压力。**
    澄清：10 人以内的房间中，白板与光标消息的总量仅为每秒几 KB 到几十 KB，服务器出口带宽并非瓶颈；真正的瓶颈在于广播的 O(N²) 放大、服务端事件循环的背压，以及浏览器主线程的解析与重绘开销。
    对策：房间分片 + 单房间人数上限；只推送脏增量；光标事件限频与批量合并；高频消息采用紧凑二进制编码（坐标用 Int16 量化），JSON 仅用于低频控制消息（Protobuf 作为可选优化，收益不足时不引入）；渲染层用 Canvas 分层 + requestAnimationFrame 合帧，避免“每条消息触发一次重绘”。
  - **难点2：网络可达性与 NAT 穿透。**
    澄清：宿舍/校园网常见对称 NAT、AP 客户端隔离（同网段设备互不可见）与 UDP 限速，这些场景下 P2P 可能直接失败；而在真正同一局域网内，ICE 通常直接选中 host 候选，并不需要 STUN。
    对策：配置多个 STUN 服务器 + 自建 TURN（coturn）兜底；ICE 失败或只选中 relay 时显式降级到服务器中转/HTTP 上传，并给出可见的界面提示；不承诺“一定 P2P”，而是把“直连成功率”作为一项实测指标。
  - **难点3：安全上下文与部署门槛。**
    澄清：非 HTTPS/localhost 环境下 getUserMedia 与文件相关 API 不可用，内网自签证书在移动端体验较差，这是许多同类方案在真实宿舍环境中“跑不起来”的原因。
    对策：节点默认生成自签证书并提供一次性信任引导；部署文档给出三种方式（localhost、内网自签、公网域名 + 正式证书）及其适用场景。
  - **难点4：大文件传输的可靠性与断点续传。**
    澄清：HTTP 路径的续传只需分片位图；P2P 路径要求双方同时在线，断线后需重建 DataChannel 并恢复分片位图，实现复杂度明显更高。
    对策：本期把“可靠续传”限定在 HTTP 路径，P2P 路径只保证会话内续传，超出即提示改用节点直传；统一以分片 hash + 整文件 hash 做完整性校验。

## 四、 实验设计与性能评估

- **4.1 实验环境搭建**

  - 网络环境：千兆以太网、百兆以太网、Wi-Fi 5 与 Wi-Fi 6（同网段）、跨网段校园网、4G/5G 各一组，用于覆盖“理想内网”与“受限网络”两类场景。
  - 测试终端：PC 浏览器（Chrome/Edge/Firefox 最新版）、一台中端安卓手机（用于 CPU 与移动端体验对比）。
  - 对照组设置：白板同步以“无节流的逐条广播”为基线；文件传输以“公网中转 HTTP”为基线；语音在“无丢包”与“注入丢包”两种条件下对比。

- **4.2 实验指标与测试方法**

  - **操作同步延迟**：测量 A 端注入绘图操作到 B 端渲染完成的时间差，使用 Performance API 打点。方法学说明：两端时钟不同步，直接用绝对时间戳作差会引入系统性误差，因此采用两种互补测量——(a) 单端回环测量，量化本地渲染与事件循环开销；(b) 以服务器下发的时间基准做粗同步后再测跨端延迟，并报告时钟偏差的量级与校正方法。每组重复不少于 30 次，报告 p50 与 p95。
  - **一致性正确性（与延迟同等重要）**：以脚本模拟 N 个客户端随机并发操作（增/删/移动图形，并注入随机延迟与乱序），检验最终状态是否收敛、是否出现图形丢失或重复；记录冲突发生次数与收敛所需时间。
  - **并发能力与资源占用**：白板房间按 5/10/20 人做压力测试，记录服务端 CPU、内存、消息丢失率与延迟分布。语音房间因受 Mesh 上限约束，按 3/5/6 人测试，并单独记录超出上限时的表现（如实呈现 Mesh 的局限，而非给出笼统的“20 人可用”结论）。
  - **文件传输对照实验**：三条路径（公网中转 HTTP / 局域网 HTTP 直传 / DataChannel 直传）× 三个量级（10 MB / 100 MB / 1 GB），每组不少于 30 次，记录平均速率、p95 耗时与两端 CPU 占用；额外测试“传输与语音并发”时的速率与 MOS 变化，用以验证 QoS 优先级策略是否有效。
  - **语音质量**：在 0% / 3% / 5% 随机丢包与人为抖动条件下采集音频，按 ITU-T P.800 的简化方法做主观评分，同时记录 RTT、抖动、丢帧率与带宽占用。
  - **边界与异常条件**：跨网段、AP 隔离、ICE 失败、断网重连等场景下系统是否按预期降级，是否给出用户可理解的界面提示。

- **4.3 预期结果**

  - MVP 功能全覆盖：多人绘图与光标同步、实时语音、文件上传与局域网直传、断点续传、文字消息。
  - 达成 1.3 中的量化指标，并产出可复现的测试脚本与原始数据表。
  - 形成若干工程结论：典型局域网环境下 HTTP 直传与 DataChannel 的吞吐差异及瓶颈归因；CRDT 方案在 N 人并发下的收敛表现与数据量增长规律；Mesh 语音的人数上限实测值。

## 五、 研究计划（进度安排）

- **第一阶段：需求分析与原型设计（第 1–2 周）**
  - 调研 WebRTC、WebSocket 与 CRDT/OT 技术栈，完成选型对比（含“为何不以 OT 为主线”的书面论证）。
  - 设计通信协议消息表与数据模型，完成 UI 原型图与模块接口定义。
  - 产出：技术选型报告 + 协议草案 + 原型图。
- **第二阶段：核心模块开发（第 3–6 周）**
  - 第 3–4 周：搭建 Node.js 信令服务器与房间管理，实现 WebSocket 白板同步（快照 + 增量）与文字消息。产出：可运行的白板 MVP。
  - 第 5–6 周：集成 WebRTC 语音（Mesh 拓扑）、成员状态与设备选择；实现 HTTP 分片上传、进度显示与断点续传。产出：语音 + 文件上传可用版本。
- **第三阶段：局域网快传与系统集成（第 7–8 周）**
  - 第 7 周：实现自托管节点的局域网服务与节点发现（mDNS/广播下沉到节点侧），打通局域网 HTTP 直传；实现 DataChannel 直传与候选对判定。
  - 第 8 周：三位一体集成、降级策略与界面状态提示。中期检查点：完成一次端到端联调演示，并确认关键技术（直传、CRDT）是否可行，必要时在此处调整范围。
- **第四阶段：性能测试与优化（第 9–10 周）**
  - 按第四章方案执行延迟、并发、传输、语音质量与一致性实验，采集并归档原始数据。
